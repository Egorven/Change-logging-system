# Change-logging-system – система ведения журнала изменений

## Назначение

Change-logging-system – приложение для учёта проектов, версий, разработчиков и изменений в программных продуктах.

Консольная версия приложения (ПР3) дополнена веб-интерфейсом на Django (ПР5),
а в ПР6 веб-интерфейс переведён на систему шаблонов Django. В ПР7 добавлен
отдельный слой SQLite с SQL-запросами и импортом данных из JSON.

Приложение позволяет:

- добавление и удаление проектов;
- добавление и сортировка версий по дате выпуска;
- добавление записей об изменениях с указанием типа, автора и даты;
- форматирование записей журнала в человекочитаемый вид;
- фильтрация изменений по категории (добавлено / исправлено / удалено);
- сортировка изменений по дате;
- получение статистики по категориям изменений;
- добавление и просмотр списка разработчиков;
- экспорт данных проекта, его версий и изменений в JSON.

## Используемые технологии

* Python 3;
* Django 5.2 – веб-фреймворк;
* HTML – разметка веб-страниц;
* Django Templates: наследование, блоки и включаемые шаблоны;
* CSS и Bootstrap 5.3 – оформление страниц;
* SVG-изображение и JavaScript;
* pytest – автоматизированные тесты;
* flake8 – проверка качества кода.

## Целевая аудитория

Разработчики и менеджеры проектов, которым необходимо вести журнал изменений в программных продуктах и отслеживать версии.

## Предметная область

Основными объектами предметной области являются:
- **проект** — программный продукт, для которого ведётся журнал изменений;
- **версия** — выпуск проекта с определённой датой;
- **разработчик** — автор изменений;
- **изменение** — запись в журнале, связывающая проект, версию и разработчика.

Разработчик может добавлять записи об изменениях в определённую версию проекта. Каждое изменение имеет тип (добавлено, исправлено, удалено), описание, автора и дату.

### Change — запись журнала изменений

Объект `Change` представляет запись об изменении в проекте.
 Файл [db/import_json.py](db/import_json.py) и SQL-файлы сохраняются как реализация
 ПР7. Текущие представления получают данные из `db.sqlite3` через Django ORM.
 На странице журнала доступны поиск по описанию, автору и разработчику,

**Основные атрибуты:**

- `author` — имя автора;
- `date` — дата изменения;
- `project` — объект `Project`, к которому относится изменение;
- `version` — объект `Version`, к которому относится изменение;
- `developer` — объект `Developer`, автор изменения.

**Основные методы:**

- `is_fixed()` — проверка, является ли изменение исправлением;
- `is_removed()` — проверка, является ли изменение удалением.

## Взаимодействие объектов

Объект `Change` связывает объекты `Project`, `Version` и `Developer`, храня ссылки на них, а не только их идентификаторы. Это позволяет напрямую обращаться к данным связанных объектов:

```python
change.project.name      # название проекта
change.version.name      # название версии
change.developer.name    # имя разработчика
```

Объект `Version` хранит ссылку на объект `Project`, к которому он относится:

```python
version.project.name     # название проекта версии
```

* `/` – главная страница: описание приложения и навигация (view-функция `index()`);

## Реализация ПР7: SQLite и SQL

JSON-файлы предыдущих практических работ сохранены как исходное хранилище.
Для ПР7 создана отдельная база [data/changelog.sqlite](data/changelog.sqlite),
не связанная с Django ORM-базой `db.sqlite3`.

В базе есть таблицы `projects`, `developers`, `versions` и `changes`.
Схема находится в [sql/schema.sql](sql/schema.sql), а каталог из 10
параметризованных запросов — в [sql/queries.sql](sql/queries.sql). Запросы
включают выборки, `WHERE`, `JOIN`, агрегатные функции, `GROUP BY` и `HAVING`.

Подключение выполняется в [db/database.py](db/database.py) через стандартный
`sqlite3`, с `row_factory = sqlite3.Row` и `PRAGMA foreign_keys = ON`.
Скрипт [db/import_json.py](db/import_json.py) переносит данные из JSON:

```text
python -m db.import_json
```

Файл [db/import_json.py](db/import_json.py) и SQL-файлы сохраняются как реализация
ПР7. Текущие представления получают данные из `db.sqlite3` через Django ORM.
На странице журнала доступны поиск по описанию, автору и разработчику,
фильтрация по типу, проекту и диапазону дат, сортировка, статистика по категориям
и постраничный вывод.

### Демонстрация показателей 11, 20 и 24

На странице `/changes/` форма поиска передаёт параметры `q`, `project`,
`date_from` и `date_to`. Представление преобразует их в проверенные условия
Django ORM. Например,
запрос `?q=ошибка&date_from=2026-09-01&date_to=2026-09-30` демонстрирует
поиск по тексту и диапазону дат одновременно.

SQL-файлы и `db/database.py` сохраняются для демонстрации реализации ПР7.
В рабочем коде [changes/views.py](changes/views.py) прямой SQL не используется:
некорректная дата обрабатывается сообщением об ошибке, а неизвестная сортировка
заменяется безопасной сортировкой по дате.

## Реализация ПР9: Django ORM

В приложении описаны четыре ORM-модели:

* `projects.Project` — проект с названием и описанием;
* `projects.Version` — версия проекта с датой выпуска и `ForeignKey` на `Project`;
* `changes.Developer` — разработчик с именем и ролью;
* `changes.Change` — изменение с типом, описанием, датой и связями с проектом,
  версией и разработчиком.

Связи доступны через `related_name`. Удаление проекта каскадно удаляет его
версии и изменения, удаление версии или разработчика обнуляет необязательную
ссылку в изменении. Структура базы управляется миграциями:

```bash
python manage.py makemigrations
python manage.py migrate
python manage.py makemigrations --check
python manage.py check
```

ORM-запросы находятся в [projects/views.py](projects/views.py) и
[changes/views.py](changes/views.py). Они используют `filter()`, фильтрацию по
связанным полям, `select_related()`, `annotate()`, `Count()`, `Q()`, `values()`,
безопасный `order_by()` и `Paginator`. Прямой SQL-слой ПР7 не используется
веб-представлениями и оставлен для сравнения подходов и проверки исходных данных.
В ПР10 административная панель настроена для моделей проекта, а SQL-запросы ORM
можно анализировать через Django Debug Toolbar.

## Реализация ПР10: Django Admin и расширенный ORM

В административной панели зарегистрированы модели `Project`, `Version`,
`Developer` и `Change`. Для них настроены столбцы списков, поиск, фильтры,
сортировка, пагинация и отображение связанных объектов через inline-формы.

Подробные страницы проектов используют slug-адреса вида
`/projects/changelog-tracker-1/`. Модель `Project` предоставляет метод
`get_absolute_url()`, а поле `name_length` реализовано через `GeneratedField` и
вычисляется базой данных. Общие данные `site_name` и `projects_count` передаются
в шаблоны через контекстный процессор `projects.context_processors.project_context`.

Для локального анализа SQL подключён Django Debug Toolbar. Панель доступна
только при `DEBUG=True` по адресу `/__debug__/` и не предназначена для production.

### `projects/`
Django-приложение, отвечающее за проекты и версии:
* `views.py` – view-функции `projects()` и `project_detail()`;
* `templates/projects/` – шаблоны списка и страницы проекта;
* `urls.py` – маршруты приложения;
* `models.py` – заготовка приложения; предметные объекты загружаются из JSON.

### `changes/`
Django-приложение, отвечающее за изменения:
* `views.py` – view-функции `changes()` и `change_detail()`;
* `templates/changes/` – шаблоны списка и страницы изменения;
* `urls.py` – маршруты приложения;
* `models.py` – заготовка приложения; предметные объекты загружаются из JSON.

### `templates/`

Общие шаблоны проекта:

* `base.html` — базовый шаблон с блоками `title` и `content`;
* `404.html` — собственная страница ошибки;
* `includes/navigation.html` — повторно используемая навигация.

### `models/`
Классы предметной области и функции работы с ними (пакет ПР3):
* `project.py` – класс `Project` и функции работы с проектами;
* `developer.py` – класс `Developer` и функции работы с разработчиками;
* `version.py` – класс `Version` и функции работы с версиями;
* `change.py` – класс `Change` и функции работы с изменениями.

### `storage.py`
Отвечает за загрузку и сохранение данных.
Выполняет преобразование:
* JSON → объекты Python;
* объекты Python → JSON.

### `utils.py`
Содержит вспомогательные функции консольного ввода:
* `input_int()` – безопасный ввод целого числа;
* `input_date()` – безопасный ввод даты;
* `input_text()` – безопасный ввод текста.

### `tests/`
Содержит автоматизированные тесты проекта.

## Запуск приложения


Веб-версия (Django):
```text
 manage.py runserver
```
После запуска открыть в браузере адрес:
```text
http://127.0.0.1:8000/
```

Консольная версия (сохранена):
```text
python main.py
```

## Тестирование

Для запуска автоматизированных тестов выполнить:
```text
pytest -v
```


## Проверка качества кода

Для проверки соответствия кода требованиям PEP 8 используется `flake8`.

Команда проверки:
```text
flake8 . --extend-exclude=venv
```

## Проверка результата ПР7

В рамках ПР7 выполнены следующие требования:

- создан отдельный слой данных на SQLite;
- разработана структура предметной области и таблицы базы данных;
- определены первичные и внешние ключи;
- создан модуль подключения к базе данных `db/database.py`;
- создан скрипт импорта данных `db/import_json.py`;
- данные из JSON перенесены в SQLite;
- создан файл `sql/schema.sql` с командами создания таблиц;
- создан файл `sql/queries.sql` с проверенными SQL-запросами;
- реализованы запросы `SELECT`, `WHERE`, `JOIN`, `COUNT`, `GROUP BY` и `HAVING`;
- все пользовательские значения передаются в SQL через параметры `?`;
- в Django-представлениях используется `sqlite3.Row`;
- страницы проекта получают данные из SQLite;
- реализованы фильтрация, поиск и статистика журнала изменений;
- README обновлён и соответствует текущему состоянию проекта;
- проект проходит автоматические проверки.

Проверка выполняется командами:

```bash
python manage.py check
pytest -v
flake8 . --extend-exclude=venv
```
